五条最值得先跑的命令

命令看什么
pytest -q全量回归，应当是绿的
pytest -m "smoke and not destructive"PR 门禁口径：9 条，0.9 秒
pytest -m scope -vfixture 作用域的可观测证据
pytest -m contract --schema-drift应当变红 4 条：验证契约测试真的会拦

实测数据：单进程 2.78 秒，4 worker 并行 6.05 秒。 并行反而慢——因为每个 worker 都要独立起靶机、独立导入。 这说明一个常被忽略的事实：并行有固定开销，用例数少于一两百条时不要开。 面试里讲出这一句，比说「我用了 xdist」有价值得多。

1pytest 工程化能力

1.1 fixture 作用域：怎么选，不是背的

作用域用在哪本仓库实例判断标准
session建连接池、登录一次lab_server、api构造贵 + 无状态污染
module本文件共用的只读数据spec（OpenAPI 文档）解析一次就够
function会写库、要干净状态book_factory、clean_library用例会改数据
tests/api/test_scope_demo.py 用构造计数器把三种作用域跑给你看。 为什么不用 id()：CPython 会复用刚释放的内存地址， id 相同不代表同一个对象，拿它做断言会写出时红时绿的假证据。

1.2 conftest 三层：判断规则只有一句

conftest.py            环境、靶机、策略        ← 换项目还能用
tests/conftest.py      业务 fixture            ← 换项目就要改
tests/api/conftest.py  子目录专属前置条件      ← 只有这里需要

一行代码放哪层，只问：换个被测系统，这行还成立吗？ 成立往上，不成立往下。

同名 fixture 子层覆盖父层，「局部特化、全局兜底」天然成立，不需要额外机制。 本仓库里 clean_library 一开始放在 api/， 后来 contract/ 也要用，就上提到了 tests/conftest.py—— 这就是分层该有的演进方向。

1.4 marker：分组决定 CI 跑什么

marker含义跑在哪一档
smoke冒烟，30 秒内跑完PR 门禁必跑（9 条）
regression回归主干合并前
contract契约测试主干 + 夜间漂移演练（11 条）
destructive会写数据PR 上排除；--env prod 自动 skip
slow耗时用例仅夜间
scope作用域教学本地学习用，CI 不跑

--strict-markers 打开后，写错 marker 名直接报错。不打这个开关， 「标签打了但没生效」可以隐藏很久——你以为在跑冒烟，实际一条都没跑。

1.5 插件：两个必须知道的坑

坑一：--dist loadscope 而不是默认的 load。 同一模块的用例落在同一 worker，模块级 fixture 和共享状态才成立。 默认 load 按单条分发，同一个文件被拆到两个进程， 模块级计数器和共享靶机会直接错乱。
坑二：--reruns 绝不能写进全局 addopts。 test_permanent_failure_is_not_masked 就是在演示这个： 真实的 5xx 缺陷会被同一次运行内的重试吃掉，CI 从此永远绿。 重试只能按用例打 @pytest.mark.flaky(reruns=3)。

2接口测试的「真本事」

2.1 令牌流转：当状态机测，不是测「能不能登」

2.2 数据依赖与清理

book_factory 是 yield 工厂：创建 → 用例逻辑 → 用例结束自动删除。

清理必须容错（接受 204 or 404）。如果清理也 assert 状态码， 会出现「因为清理失败而失败」的红——这是最误导人的一种，因为它让你去查业务， 问题却在前一轮用例里。

不要依赖库里预置的数据。所有需要精确计数的用例（分页）用 clean_library 显式重置，而不是赌「上次跑完留下的状态刚好对」。 接真实靶场时这个 fixture 会自动 skip，不会假装成功。

2.3 schema 校验：两层不是重复

层来源表达什么
models.py本地手写 pydantic「我期望的数据」
contracts.py手写 JSON Schema「服务端承诺的结构」
/openapi.json服务端发布「服务端实际发布的契约」

实测：把 published_year 从 int 改成 str 之后——

pytest -m contract --schema-drift
FAILED test_list_response_matches_schema          # 本地 schema 拦住
FAILED test_item_response_matches_schema          # 本地 schema 拦住
FAILED test_pydantic_and_jsonschema_agree         # pydantic 放过了！
FAILED test_live_response_conforms_to_openapi     # OpenAPI 契约拦住
pydantic 默认 lax 模式："1991" 会被自动转成 1991，校验通过。 jsonschema 不会做这种转换。这就是必须要两层的原因—— pydantic 写起来方便，但对类型漂移不敏感； 只用它，等于给上游悄悄改字段类型开了绿灯。

2.4 401 与 403 的分界

401 = 我不知道你是谁

缺令牌、令牌无效、令牌过期、令牌被吊销
test_forged_token_is_rejected
test_logout_invalidates_access_token

403 = 我知道你是谁但不能做

已认证，权限不足
test_normal_user_cannot_read_admin_stats
test_cannot_delete_others_book

越权用例还多断言一句：403 之后数据必须还在。只看状态码不看结果， 会漏掉「返回 403 但已经删了」这种最危险的实现。

3CI/CD 落地

三个设计决策

PR 不跑 destructive

写操作用例在 PR 上跑，一旦有并发提交就互相踩数据， 红得毫无规律，很快就被人忽略掉。

--env prod 是硬守卫

pytest_collection_modifyitems 在收集阶段就打 skip， 不依赖人记得加参数。写了 destructive 的用例在生产环境永远不会被执行。

报告自包含

--self-contained-html：单文件、无外链， 下载下来双击能看，不用起服务。

接真实环境时把 job 里的 run 换成 pytest -m smoke --base-url "${{ secrets.STAGING_BASE_URL }}" --env staging， 地址与凭据放 GitHub Secrets。

4五个刻意埋下的坑

都是真实项目里踩过的，故意留在靶机里让你遇到一次。

坑表现根因 / 修法
401 时不读请求体 刷新令牌莫名失败，报 400 或读不到请求行 HTTP/1.1 长连接：未读字节留在 socket 里，下一个请求被顶掉。必须在路由前把 body 读完
分页 size 回显 len(items) 最后一页只有 5 条时回 size=5，前端算错总页数 必须回显请求值。test_page_count_is_ceiling[size=50] 抓这个
reset() 顺手关掉漂移开关 「明明开了 --schema-drift，契约测试却全绿」 配置与业务数据必须分开重置，否则出现假阴性
用 uuid 做 flaky 用例的 key 测试稳定失败且看不出原因 重试会重新执行函数体，每次都是新 key，故障永远停在「第一次」。改用 request.node.nodeid
--reruns 写进全局 addopts 真 bug 被重试吃掉，CI 永远绿 只按需打 @pytest.mark.flaky，全局配置开重试等于关掉了门禁

6面试问答映射

Q：fixture 作用域你怎么选？
先看构造代价，再看是否污染状态。连接池、只登录一次这类昂贵且无状态的放 session； 本文件共用的只读数据放 module；会写数据的放 function。我用构造计数器验证过， 不用 id()——CPython 会复用内存地址，id 相同不代表同一个对象。
Q：conftest 你怎么分层？
三层：根层放环境和策略，换项目还能用；业务层放客户端和数据工厂，换项目就要改； 子目录层放局部前置条件。判断标准是「换个被测系统这行还成立吗」。 同名 fixture 子层覆盖父层，局部特化天然成立。
Q：接口测试的鉴权你怎么测？
当状态机测，不只测能不能登：登录拿 access+refresh → access 过期时客户端必须透明续期一次 → refresh 必须一次性（防重放）→ logout 后 access 立刻失效。 服务端要把 TOKEN_EXPIRED 和 INVALID_TOKEN 分成两个 code，否则前端只能一律踢回登录页。
Q：你的用例怎么处理数据依赖？
yield 工厂，用例自己造、自己清，清理容错（接受 204 和 404）。 需要精确计数的用例显式重置，不依赖预置数据。清理不 assert 状态码—— 否则会红在「清理失败」，误导排查方向。
Q：schema 校验你用什么？
两层。pydantic 表达「我期望的数据」，JSON Schema 表达「服务端承诺的结构」， 再从服务的 OpenAPI 拿第三个来源。实测把 int 字段改成 str， pydantic 的 lax 模式会放过，jsonschema 和 OpenAPI 契约能拦住——这就是两层的意义。
Q：不稳定用例你怎么处理？
先分类：瞬时故障按用例打 reruns，永久故障绝不重试。 --reruns 不能写进全局 addopts，否则真 bug 被重试吃掉、CI 永远绿。 我会写一条「永久故障必须红」的用例来验证这点没被破坏。
Q：你的测试怎么进 CI？
三档。PR 只跑 smoke 且排除 destructive，60 秒内出结论； 主干跑全量并上 Python 矩阵，fail-fast 关掉； 夜间跑 slow 和契约漂移演练。生产环境用 --env prod 在收集阶段就 skip 掉写操作用例。
Q：什么时候不该用并行？
用例少的时候。我实测 79 条：单进程 2.78 秒，4 worker 6.05 秒—— 并行反而慢，因为每个 worker 要独立起靶机、独立导入。 并行有固定开销，一两百条以下不开。开的时候用 --dist loadscope， 保证同模块在同一 worker，模块级 fixture 才成立。

7换公网靶场练（可选）

本地靶机跑通之后，可以换真实服务验证同一套工程能力。靶场只是载体， 换的时候只改 client.py，用例断言逻辑不动。

靶场能练什么坑
httpbin.orgfundamentals：状态码、header、重定向、响应结构无状态无鉴权，练不到 token 流转；国内访问不稳
Restful-bookertoken 鉴权、CRUD 闭环、yield 清理托管在公网，冷启动慢；写操作不真落库
DummyJSON参数化、分页、超时重试支持 ?delay= 参数，正好用来练超时断言
Practice Software Testing全栈 + CI 门禁 + 缺陷报告注册会限流，用站点提供的固定账号
再往后是给真实开源仓库补测试（open-webui / dify / ragflow / langflow）。 核心纪律：一个 PR 只做一件事、改动 200 行以内、先开 issue 问一句再动手。 第一个 PR 的最佳切入点通常是补边界用例或修 CI 里的不稳定用例，不是加新功能。
