Phase 03 · 主线项目

RAG 质量评测平台 · 开工蓝图

目标不是再造一个 RAG 应用，而是造一把能给别人用的尺子：对任意 RAG 问答系统，用可版本化的评测集、可校准的指标、可对比的基线，判断一次改动到底是变好还是变差。

Python 3.11 pytest + httpx + Ragas SQLite + Jinja2 报告 GitHub Actions 预计 3 周 / 39 小时
01

项目定位与验收标准

一句话定位：一个面向 RAG 系统的自动化质量评估工具链，支持评测集版本化、多层级指标、基线回归对比与安全套件。

它必须满足四个硬性验收条件，缺一个就不算做完：

验收项具体标准为什么这条重要
可替换换被测系统只改 YAML，不改一行代码证明你会做适配层抽象，而不是写死脚本
可复现同一评测集两次运行，指标差异在抽样误差内证明你的数字可信，不是随手编的
可判定每个指标有阈值，超阈值即失败并有归因证明这是测试，不是"跑个分看看"
可回归与基线对比能输出"显著变好/变差/无变化"这是面试里最能打的一个点
范围控制：明确不做模型训练、不做 UI 前端、不自建向量库。被测对象通过 HTTP 调用，评测平台只负责"提问、收集、打分、对比、报告"。
02

技术选型与取舍理由

选型原则：每一项都要能在面试里回答"为什么是它、为什么不是另一个"。所以下表同时写了不选什么。

层选型选择的理由没有选什么
运行时Python 3.11 + uvAI 生态默认语言；uv 装依赖快、锁文件确定，CI 可缓存Poetry 解析慢；裸 pip 无锁文件
测试框架pytest 8 + pytest-asyncio + xdist招聘市场通用，插件生态最全，异步与并发都覆盖unittest 冗长；自研 runner 无法复用生态
HTTP 客户端httpx同步异步同一套 API，支持超时细分与连接池requests 无原生异步，并发评测会成瓶颈
数据模型pydantic v2评测集、配置、结果共用一套校验，脏数据在入口就拦dataclass 无运行时校验；裸 dict 无法演进
配置pydantic-settings + YAML支持分层覆盖与环境变量注入，密钥不进仓库纯 .env 表达不了嵌套结构；纯代码配置不可复用
评测集JSONL + JSON Schema逐行 diff 友好、可人工审阅、可增量追加Excel 难版本化；数据库对贡献者门槛高
生成指标Ragas 0.2faithfulness / relevancy / context 指标齐全，社区活跃全自研成本高且指标无对照；DeepEval 作为补充而非主力
检索指标自研（约 80 行）hit@k、MRR 算法简单，自己写可控、可解释、面试可讲引入框架反而遮蔽了原理，被追问就露怯
裁判模型可配置，默认 OpenAI 兼容端点（DeepSeek / Qwen / 本地 Ollama）成本可控、数据不出域、切换只改配置写死 GPT-4 既贵又有合规风险，且不可离线演示
存储SQLite + 结果 JSON零运维、单文件可带走、支持 SQL 查询历史Postgres 对单人项目是过度设计
报告Jinja2 → 单文件 HTML（CSS 内联）可离线打开、可当 CI artifact、可邮件发送Allure 太重且定制成本高
统计bootstrap 置信区间（numpy）+ scipy 配对检验避免"提升 3%"其实在噪声里只比均值是最常见的低级错误
一致性scikit-learn cohen_kappa_score标准实现，报告里可直接给数字手算 kappa 容易错，且不可信
安全套件自研注入集 + promptfoo（夜间补充）自研集能接入统一评分；promptfoo 补红队模板只用 promptfoo 则与自有指标割裂
工程规范ruff + mypy + pre-commit提交即拦截低级问题，体现工程素养无 lint 的仓库在评审时会被扣分
CIGitHub Actions免费额度够用，且面试官点开就能看到运行记录Jenkins 本地不可见，失去"可验证"价值
关键约束：核心链路必须能在没有 API Key的情况下跑通（用 mock target + 规则型指标）。否则你的项目在别人机器上、在 CI 里都是死的，这会被直接判定为"不可复现"。

04

核心接口契约

整个项目只有四个核心抽象。把这四个定清楚，剩下都是填空。下面的代码可以直接作为开工的第一版。

4.1 领域模型

from typing import Literal
from pydantic import BaseModel, Field

Slice = Literal["core", "boundary", "refusal", "adversarial", "security"]

class PassageRef(BaseModel):
    doc_id: str
    chunk_id: str | None = None

class Case(BaseModel):
    id: str = Field(pattern=r"^[a-z0-9_\-]+$")
    slice: Slice
    question: str
    expected_answer: str | None = None      # 参考答案，可为空
    expected_passages: list[PassageRef]     # 黄金证据，检索层用它算指标
    must_refuse: bool = False               # 是否应当拒答
    tags: list[str] = []

class Passage(BaseModel):
    doc_id: str
    chunk_id: str | None = None
    text: str
    score: float | None = None

class Answer(BaseModel):
    case_id: str
    text: str
    contexts: list[Passage] = []            # 系统实际召回的内容
    latency_ms: int = 0
    prompt_tokens: int = 0
    completion_tokens: int = 0
    error: str | None = None                # 采集失败也落库，不吞异常

class MetricScore(BaseModel):
    name: str
    value: float
    threshold: float
    passed: bool
    detail: dict = {}                       # 归因信息：命中哪条、差多少

4.2 被测系统适配协议

from typing import Protocol

class Target(Protocol):
    name: str
    version: str                            # 写进 run 元数据，用于基线对比

    def ask(self, case: Case) -> Answer:
        """单条提问。实现方负责超时、异常包装；不得抛出未捕获异常。"""
        ...

    def health(self) -> bool:
        """开跑前自检，避免把环境故障算成质量下降。"""
        ...

这条协议是整个项目的唯一扩展点。新增 Dify、RAGFlow、FastGPT、Coze，都只是实现它。面试时这句话比"我做过 RAG 评测"有力得多。

4.3 评测器协议

class Evaluator(Protocol):
    name: str
    threshold: float
    requires_context: bool                  # 是否需要召回内容
    requires_reference: bool                # 是否需要参考答案

    def score(self, case: Case, answer: Answer) -> MetricScore:
        ...

统一成同一个签名后，检索指标、生成指标、安全指标可以混在一个列表里跑，报告层不需要知道具体实现。阈值不在代码里写死，从 suite 配置读——这样同一套指标可以在 smoke 和 regression 用不同阈值。

4.4 执行器主循环（伪代码）

def run(suite: Suite, target: Target, evaluators: list[Evaluator]) -> Run:
    assert target.health(), "被测系统不可用，拒绝开跑"

    cases = load_cases(suite.datasets).filter(suite.selectors)

    with ThreadPoolExecutor(max_workers=suite.concurrency) as pool:
        answers = list(pool.map(lambda c: ask_with_retry(target, c, suite.retry), cases))

    results = []
    for case, answer in zip(cases, answers):
        for ev in evaluators:
            if not ev.precondition_ok(case, answer):
                continue
            results.append(RunRecord(case=case, answer=answer, score=ev.score(case, answer)))

    return store.save(run_meta(target, suite), results)
两个容易被忽略的工程细节：① 采集失败必须落库并单独统计，否则"系统挂了"会被误算成"质量下降"；② 重试只对 5xx 和超时生效，对 4xx 重试是掩盖问题。
05

数据流

一次完整运行分五段：加载校验、采集答案、多指标打分、落库、对比出报告。分段的意义是每段都能单独测试。

06

评测集规范

评测集是这个项目最值钱的资产，比代码重要。它决定了你的数字有没有意义。三类切片的写法完全不同，不能混着凑数。

切片数量写法要求用哪些指标判定
core80答案能在语料中直接找到，必须标注 expected_passages检索 + 忠实度 + 相关性
boundary30歧义问法、多跳推理、超长上下文、跨文档冲突正确答案率 + 一致性
refusal20语料里确实没有答案，正确行为是拒答而不是编造拒答正确率 + 过度拒答率
adversarial20诱导性提问、前提错误、要求超出范围的内容拒答或纠正率
security45直接注入、间接注入（污染文档）、工具调用劫持攻击拦截率 + PII 泄露率

6.1 单条样例

{
  "id": "core_refund_policy_01",
  "slice": "core",
  "question": "订单签收后第 9 天还能无理由退货吗？",
  "expected_answer": "不能，七天无理由退货的期限为签收后 7 天内。",
  "expected_passages": [
    {"doc_id": "policy_return_v3", "chunk_id": "c012"}
  ],
  "must_refuse": false,
  "tags": ["售后", "时效"]
}

6.2 编写规则（贴进 CONTRIBUTING）

  1. 一个 case 只考一个意图。同时考"能不能召回"和"会不会拒答"的用例，失败时无法归因。
  2. expected_passages 必须指向真实存在的 chunk。加载期用脚本校验，指向不存在的 chunk 直接报错。
  3. 问题用真实用户的口吻写，不要用文档里的标题改写。后者会系统性高估召回率。
  4. 必须能独立判定通过与否：两个人看同一条 case 应得出相同结论，否则重写。
  5. 新增 case 走 PR，附一句"为什么需要这条"，避免评测集堆成无意义的数量。
数量与质量：80 条精心标注的 core 集，比 500 条自动生成的问题有用得多。面试官如果追问"你的评测集怎么保证质量"，答案就在这里：切片设计 + 双人一致性抽检 + 与真实用户问题分布对齐。
07

指标清单与阈值

阈值不是拍脑袋定的：先跑一版基线，把当前值减去合理提升空间作为初始阈值，再根据业务风险调整。下表给的是可用的起点。

指标层算法要点初始阈值失败意味着
hit@k检索期望 chunk 是否出现在 top-k≥ 0.90语料没覆盖 / 切分不合理 / embedding 不适配
recall@k检索命中数与期望 chunk 总数之比≥ 0.85多跳问题只召回一半证据
MRR检索首个正确结果排名的倒数均值≥ 0.75证据存在但排序靠后，rerank 有问题
faithfulness生成答案中的论断能否被召回内容支撑≥ 0.85幻觉，模型在编造
answer_relevancy生成答案与问题的语义相关度≥ 0.80答非所问，提示词跑偏
context_precision生成召回内容中有用部分的比例≥ 0.70召回噪声多，浪费上下文窗口
refusal_accuracy行为该拒答时是否拒答≥ 0.90编造答案，是最高危的缺陷
over_refusal_rate行为不该拒答却拒答的比例≤ 0.10过度保守，产品不可用
injection_block_rate安全攻击用例被正确拒绝或忽略≥ 0.95存在可被利用的提示词漏洞
pii_leak_rate安全输出中出现未脱敏个人信息≤ 0.01合规风险，必须阻断发布
p95_latency性能端到端 P95，按并发分档≤ 8000ms体验不可接受，需查检索或模型调用
self_consistency生成同 case 三次采样的语义一致率≥ 0.90输出漂移，不适合做确定性业务
分层归因的逻辑：faithfulness 低但 recall 正常 → 生成层问题；recall 低 → 检索层问题；两者都正常但 refusal 错 → 提示词或策略问题。面试时按这个顺序讲，会被认为"有方法论"。
08

报告与基线对比设计

报告的唯一目标是让人在 3 分钟内做出"能不能发"的决定。所以顺序是：结论 → 告警 → 下钻 → 证据。

第一屏：结论卡

通过率、失败指标数、P95 延迟、单次成本、与基线相比的红黄绿。不放任何曲线。

第二屏：回归告警

只列变差的指标，按影响面排序，标明是否显著（置信区间是否跨 0）。

第三屏：切片下钻

按 slice 与 tag 分组，看是哪类问题在拖低整体，避免均值掩盖局部崩塌。

第四屏：失败用例 TopN

每条含问题、答案、召回片段、失败指标、差距值。可直接复制去建 issue。

8.1 显著性怎么算

def bootstrap_ci(values, n_boot=1000, alpha=0.05):
    rng = np.random.default_rng(42)
    means = [rng.choice(values, size=len(values), replace=True).mean() for _ in range(n_boot)]
    lo, hi = np.quantile(means, [alpha / 2, 1 - alpha / 2])
    return float(lo), float(hi)

def compare(baseline, current):
    delta = current.mean() - baseline.mean()
    lo, hi = bootstrap_ci(np.array(current) - np.array(baseline))
    verdict = "无显著变化" if lo <= 0 <= hi else ("显著提升" if delta > 0 else "显著下降")
    return {"delta": round(delta, 4), "ci": (round(lo, 4), round(hi, 4)), "verdict": verdict}

用配对 bootstrap（对同一批 case 做差再重采样）而不是两组独立重采样，因为 case 是配对的，独立采样会高估方差。

面试高频追问："你的提升 3% 是真的吗？"标准答案是：给出配对 bootstrap 的 95% 置信区间；如果跨 0 就说明在抽样噪声内；如果样本量小，再补一个配对 t 检验或 Wilcoxon 作为交叉验证。

CI 流水线设计

触发跑什么时长目标失败后怎么办
PR单测 + 适配层契约 + 30 条 core 冒烟（mock target）< 5 分钟阻断合并，输出失败用例与差异
合入主干150 条回归（真实被测系统，secrets 注入）< 20 分钟标记基线候选，人工确认后可更新基线
夜间全量 + 安全套件 + 裁判一致性漂移检测< 60 分钟开 issue，附报告 artifact
每周成本报告：token 消耗、单 case 平均成本—超预算告警
 
name: ci
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run pytest tests/unit tests/contract -q
      - run: uv run rag-eval run --suite smoke --target mock --report out/report.html

为什么 PR 用 mock：真实模型调用有随机性和费用，放进 PR 门禁会制造 flaky。mock 只验证"链路通、断言生效、报告能生成"，质量的真实变化交给主干与夜间任务。这个取舍本身就是可以讲的设计决策。

十天开工顺序

按这个顺序做，每天结束都有可运行的东西。不要先写报告模板再补数据——顺序反了会返工。

  1. Day 1 建仓库、pyproject、ruff/mypy、目录骨架、README 占位。
  2. Day 2 models.py + config.py + cli.py 骨架，跑通 rag-eval --help。
  3. Day 3 Target 协议 + mock target，实现确定性假答案，能跑出 5 条结果 JSON。
  4. Day 4 dataset.py + JSON Schema，写 30 条 core 用例，加载期校验生效。
  5. Day 5 retrieval.py 三个指标 + 单测（手工造数验算，误差必须为 0）。
  6. Day 6 http_rag 适配真实系统，接上第一批真实答案；处理超时与异常落库。
  7. Day 7 generation.py 接 Ragas，先只跑 faithfulness 与 relevancy，看数值是否合理。
  8. Day 8 judge.py + 50 条人工标注 + kappa 校准，形成第一版可信裁判。
  9. Day 9 store.py + baseline.py + 报告模板，产出第一份带 diff 的 HTML。
  10. Day 10 CI 三档流水线 + 安全套件接入，跑一次夜间任务，写缺陷报告初稿。
第 3 天就能跑起来的意义：很多人的项目死在"想先把指标写完美"。先用 mock 打通端到端，后面每一步都是在活的系统上改，反馈快十倍。

风险与降级方案

风险表现降级方案
没有 API 额度跑不起来，CI 全红mock target + 规则型指标（关键词、引用覆盖率）保底；裁判用本地 Ollama 小模型
模型输出波动大同一评测集两次分数差很多固定 seed、缓存答案、同 case 多次采样取均值、报告标注采样次数
裁判成本高150 条 × 4 指标费用超预算抽样评测（每切片抽 30%）、结果缓存、只在夜间跑全量
限流与超时大批 429 / 超时被算成失败指数退避、并发上限、把执行错误与质量失败分开统计
评测集质量差指标好看但真实体验差抽 20% 双人标注算一致性、与线上真实问题分布对齐、每季度淘汰过时 case
裁判偏好漂移换模型版本后分数整体抬升固定裁判版本、每次换版本重跑锚点集、报告记录裁判版本号
