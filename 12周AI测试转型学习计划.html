OVERVIEW

总览：四个阶段怎么串起来

阶段一解决"能不能写"，阶段二解决"懂不懂 AI"，阶段三解决"有没有证据"，阶段四解决"会不会讲"。任何一段跳过，面试都会在对应环节暴露。

阶段周次核心问题收口产出验收标准
一 工程底座W1–W4能不能写出别人能跑的测试代码带 CI 门禁的接口测试仓库clone 后一条命令跑通并出报告
二 AI 认知W5–W8知不知道 AI 系统哪里会坏分层测试方案 + 指标实验记录能把一次答错定位到具体层
三 项目实战W9–W11有没有可验证的实战证据RAG 评测平台 + 缺陷报告 + PR有量化指标、有真实缺陷、进了 CI
四 面试定向W12能不能讲清楚并且被录用量化简历 + 6 个 STAR 故事3 分钟讲透主线项目
时间纪律：每周只允许一个"未完成的产出物"。宁可把 W7 的 judge 校准做扎实，也不要把 W7、W8 各做一半——项目实战阶段会把这个欠账放大成讲不清的空白。
PHASE 01

工程底座：把测试写成工程

W1 – W4 · 52h

这一阶段不要碰 AI。目标只有一个：让别人 clone 你的仓库，一条命令跑完全部测试并拿到报告。没这个底子，后面所有 AI 指标都只是脚本 demo。

优先用本地靶场：同目录的 api-lab/ 是一个已跑通的练手仓库（79 条用例，内置本地 REST 靶机，不联网、不装 Docker），覆盖 W1–W4 全部能力点：conftest 三层分层、fixture 作用域对照实验、三种参数化、marker 分组、xdist / rerunfailures / html 插件、令牌状态机、数据工厂与清理、pydantic + jsonschema + OpenAPI 三层契约、CI 三档流水线。配套说明见《阶段一工程底座练手手册》。建议先把它跑通并改坏几次，再用下面的公网靶场验证同样能力——公网靶场受网络与限流影响，不适合做 CI 里的唯一依赖。
周次练手靶子练什么选它的理由
W1httpbin + JSONPlaceholderfixture 分层、状态码、断言结构零门槛、免注册，先把工程骨架跑通
W2Restful-bookertoken 鉴权、CRUD、yield 清理有完整的鉴权与数据生命周期，契约清晰
W3DummyJSON参数化、分页、异常分支、并行业务字段真实，适合练断言设计与 flaky 治理
W4Practice Software Testing全栈套件 + CI 门禁 + 缺陷报告可 Docker 本地跑，自带已知缺陷可练归因
用法：每周只挑一个靶子，做完"能跑 + 能进 CI"再换。靶子只是载体，练的是你自己的仓库结构。完整清单、真实开源仓库补测试的路径、以及"第一个 PR 怎么提"，见同目录《Dify 适配接入手册 & 阶段一练手清单》。
W1

环境与 pytest 工程化

搭出一个 clone 即可运行的测试仓库骨架

13h

任务

  1. 装 uv + Python 3.11，建 src-layout 项目，配 ruff 与 mypy
  2. 拆分 conftest 层级：根级放配置日志，api 级放会话 token，e2e 级放浏览器实例
  3. 吃透 fixture 作用域，写一个 session 级 token fixture 与一个 function 级数据清理 fixture
  4. 配置 marker：smoke / regression / slow，并让 CI 能按 marker 选择性执行
  5. 写 10 条对公开 API 的用例，每个用例自带数据准备与清理

产出物

可运行仓库 + README（含一条命令跑全量的说明）

自检

W2

接口测试硬功

鉴权、数据依赖、契约校验，三样都要能独立处理

13h

任务

  1. 鉴权链路：cookie / token 刷新 / 并发下 token 失效的重试逻辑
  2. 用 yield fixture 做数据工厂，保证退出即清理；验证清理失败不会污染后续用例
  3. 响应校验：pydantic 模型校验结构，jsonschema 校验外部契约
  4. 错误分支：断言错误码与错误体结构，不硬编码文案
  5. 把浏览器 DevTools 里的真实请求批量转成 httpx 用例

产出物

20 条覆盖 CRUD 与异常分支的接口用例

自检

W3

参数化、并行与不稳定用例

让套件快起来，并且稳定到可以当门禁

13h

任务

  1. parametrize + param(id=, marks=) 做到用例名可读、可筛
  2. pytest-xdist 并行，用独立账号池解决共享资源冲突
  3. 建 flaky 清单：区分真缺陷、环境抖动、用例设计缺陷三类
  4. 失败现场留证：请求响应落盘、日志分级、--tb=short 输出
  5. 跑 pytest-cov，找出"有代码没用例"的分支并补上

产出物

100 条用例并行 < 2 分钟；一份 flaky 归因清单

自检

W4

CI 门禁与报告

这是"会写脚本"和"会做质量工程"的分水岭

13h

任务

  1. GitHub Actions：matrix、依赖缓存、secrets、artifact 上传
  2. 分层触发：PR 跑 smoke，合入主干跑 regression，夜间全量
  3. pytest-html 出报告，失败自动在 PR 留言并附报告链接
  4. 质量门禁：用例失败即阻断；关键模块覆盖率低于阈值即阻断
  5. 写一份 CI 说明文档：为什么这样分层、失败怎么处理

产出物

带徽章的仓库 + 一次真实拦截 PR 的记录

自检

阶段一准出不看学习时长，只看一件事：把仓库链接发给一个不熟的同行，他能在 10 分钟内跑起来。
PHASE 02

AI 认知：建立"哪里会坏"的心智模型

W5 – W8 · 52h

不要从 Transformer 数学开始。这四周只回答三个问题：AI 输出为什么不确定、一次答错该归因到哪一层、怎么把"感觉不对"变成可比较的数字。

W5

LLM 基础与不确定性

先亲眼看到"同样的输入，输出不一样"

13h

任务

  1. 搞清 token、上下文窗口、temperature / top_p、system prompt 的影响边界
  2. 固定一个问题采样 20 次，记录答案差异率、语义相似度、长度分布
  3. 把幻觉分成四类：事实错误、张冠李戴、过度自信、编造引用，各找两个真实例子
  4. 验证 temperature=0 是否真的稳定，记录反例
  5. 写一页结论：为什么 assert 相等在这里失效，我的替代方案是什么

产出物

不确定性实验记录（含 20 次采样原始数据）

自检

W6

RAG 架构与检索层指标

手算一遍指标，比调用框架学到得多

13h

任务

  1. 走通一条链路：文档 → 切分 → embedding → 向量库 → top-k → rerank → 生成
  2. 不用框架，手写 hit@k、recall@k、MRR 的计算脚本
  3. 对比 chunk size 256 / 512 / 1024 对召回的影响，记录实验数据
  4. 构造 30 条带标注 passage 的问题，算出检索指标基线
  5. 刻意制造两类错误：检索错 vs 生成错，练习归因

产出物

检索评测小实验 + 自研指标计算脚本

自检

W7

生成层评测与 LLM-as-Judge

本阶段最难也最值钱的一周

13h

任务

  1. ragas 跑通 faithfulness、answer_relevancy、context_precision、context_recall
  2. 做 judge 偏差实验：换选项顺序看结果是否翻转（位置偏差），加长答案看分数是否虚高（长度偏好）
  3. 人工标注 50 条，与 judge 结果算 Cohen's kappa
  4. kappa 低于 0.6 就重写 rubric，再测一次，记录两版差异
  5. 做一次 pairwise 对比：新版 prompt vs 旧版，看谁赢更多

产出物

judge 校准报告（含 kappa 数值与三类偏差实验结论）

自检

W8

安全、性能与测试方案

把前四周学的东西收成一份能拿出手的方案

13h

任务

  1. 攻击面梳理：直接注入、间接注入（RAG 文档污染）、工具调用劫持，各造 15 条用例
  2. PII 检测：正则 + 简单 NER，验证输出是否泄露手机号、邮箱、身份证号
  3. 性能与成本：P95 延迟、首 token 时间、并发 20 的降级曲线、单次查询 token 成本
  4. 写《XX 系统 AI 质量测试方案》：范围、分层策略、指标与阈值、准入准出
  5. 找一个开源 RAG 项目，通读它的测试目录，列出缺口

产出物

8 页测试方案 + 45 条安全用例 + 一份测试缺口清单

自检

阶段二准出给一个陌生 AI 应用，能在 2 小时内写出它的分层测试方案，并说清每层用什么指标、阈值定多少、依据是什么。
PHASE 03

项目实战：做出可验证的证据

W9 – W11 · 39h

主线项目只做一个：RAG 问答系统的质量评测平台。配套动作是给开源项目补测试、提 PR——面试官信第三方证据，不信自建 demo。项目结构见同目录的《开工蓝图》。

W9

骨架与评测集

先让空壳跑起来，再往里填内容

13h

任务

  1. 按蓝图搭目录，先跑通 mock target（无 API key 也能跑通全链路）
  2. 评测集 150 条：正常 80 / 边界 30 / 拒答 20 / 对抗 20
  3. 每条 case 必须写清 expected_passages 与可判定的通过标准
  4. 加 JSONL schema 校验，脏数据在加载期就报错
  5. 跑出第一份结果 JSON，哪怕指标只有两三个

产出物

v0.1 可运行 + 150 条带标注评测集

自检

W10

指标链路与基线对比

让报告能回答"这次改动变好了还是变差了"

13h

任务

  1. 检索、生成、行为三类指标统一成 MetricScore 结构
  2. SQLite 存运行历史，支持任意两次运行对比
  3. 基线 diff：绝对差值 + bootstrap 置信区间，跨 0 判"无显著变化"
  4. HTML 报告：总览卡、切片下钻、失败 TopN（含上下文）、与基线 diff
  5. 找 3 个真实用户，让他们读报告并说出结论，记录卡点

产出物

一份 3 分钟能看懂的评测报告

自检

W11

安全套件、CI 与真实 PR

把项目从"我能跑"变成"别人能用"

13h

任务

  1. 安全套件接入夜间任务，输出按严重度分级的漏洞清单
  2. CI 三档：PR 冒烟、主干回归、夜间全量 + 安全
  3. 在开源 RAG 项目里找 3 个真实缺陷，写可复现的缺陷报告
  4. 至少提 1 个 PR（补测试、修 bug、补文档均可）并跟进回复
  5. 写 docs/defect-report.md：复现步骤、根因定位、修复建议、影响面

产出物

3 个缺陷案例 + 1 个已提交 PR + 全绿 CI

自检

阶段三准出把仓库链接和缺陷报告发出去，对方能看懂你在测什么、测出了什么、为什么这算问题。做不到就回炉，不要进面试阶段。
PHASE 04

面试定向：把经历翻译成录用理由

W12 · 13h

技术到位但讲不清，等于没有。这一周只做四件事：改简历、写故事、模拟面试、开始投递。

W12

简历量化、STAR 表达与投递

把 11 周的产出压缩成 3 分钟能听懂的话

13h

任务

  1. 简历改成量化版：3 个项目，每个都有数字、技术栈、你的职责边界
  2. 准备 6 个高频题的 STAR 稿，每题 90 秒，录音回听并改到不啰嗦
  3. 模拟面试 2 次：一次同行对练，一次自问自答录屏复盘
  4. 投递 20 家，建追踪表：岗位类型、反馈、被问倒的问题
  5. 把被问倒的问题补成答案，形成个人题库

产出物

简历 v2 + 6 个 STAR 故事 + 投递追踪表

自检

阶段四准出连续三次模拟面试中，面试官的问题都能落回你准备过的三个项目；被问到陌生场景时，你能用分层的思路现场拆解。
常见翻车点：把"我熟悉 AI 测试"写在简历上，却说不出一个具体指标的名称和阈值来源。任何写在简历上的能力，都必须对应一个你能当场打开的仓库或报告。
RHYTHM

每周节奏与时间分配

13 小时不是"有空就学"，而是固定档期。建议把动手任务放在工作日晚上，把需要连续思考的任务放在周末。

时段时长做什么注意
周一至周五5 × 1h读文档、写代码、跑实验只做能在 1 小时内收尾的小块任务
周六上午4h本周主产出物的攻坚关掉消息，一次只做一件事
周日上午3h补齐自检、写复盘笔记笔记只写"卡在哪、怎么解决"
周日晚1h预习下周，准备环境与资料避免周一从零启动
进度落后怎么办：砍范围，不砍阶段。宁可把评测集从 150 条降到 80 条，也要保住"指标链路 + 基线对比 + CI"这条主线。因为面试官考的是结构，不是条目数量。
