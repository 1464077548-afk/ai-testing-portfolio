Dify 适配接入手册 & 阶段一开源练手清单

上半部分讲怎么把 rag-eval 接到真实 RAG 系统上（以 Dify 为第一靶子，已实现并通过 28 项离线契约验收）；下半部分解决阶段一"没有真实项目可练"的问题，给出可注册即用、可提 PR 的靶子清单。

适配器已实现 28 项契约测试通过 零第三方依赖 含 doctor 自检命令
01

为什么第一靶子选 Dify

选靶子不能只看"火不火"，要看它能不能吐出评测需要的数据。评测 RAG 最核心的信息是"系统到底召回了什么"，没有这个，检索层指标全部无从谈起。

候选能否返回引用片段部署成本岗位相关度结论
Dify返回 document_name / segment_id / score / content云沙箱零部署；本地约 6 个容器国内最高主靶子
RAGFlow返回 引用块与相似度本地约 4-5 个容器，吃内存较高第二靶子，可选
FastGPT部分 需开启引用，结构与 Dify 不同中等中等走 openai_compat + 自定义映射
LangChain 模板不返回 需自己加回调低（本地 Python）偏低不适合做检索评测靶子
自建 RAG可控 但要自己写自己维护低只在你没有其他选择时用
一句话理由：Dify 的 metadata.retriever_resources 是现成的评测输入。它同时给文档名、片段 ID、相似度和正文，等于把"检索可观测性"白送给你，你只需要做映射。
02

三种起步路径

路径适合谁代价注意
云端沙箱只想先跑通链路、机器带不动 Docker免费额度有限，数据出域用公开语料，别传公司文档
本地 docker compose要演示、要反复跑、要控成本约 8GB 内存 + 首次拉镜像较慢用 docker compose up -d，默认 80 端口，API 在 /v1
公司测试环境已在岗、想给现有产品做评测需要申请应用 Key务必用独立测试应用，别打生产
不要做的事：为了"更真实"直接拿生产应用当靶子。评测会高频调用、灌测试数据、甚至触发限流。用一个专门的测试应用，是基本的职业素养。
03

六步接入

  1. 建应用：Dify 里创建「聊天助手」或「Chatflow」。注意 Agent / Workflow 类型走的是别的接口，本适配器不覆盖。
  2. 灌语料：把 datasets/corpus/policy.jsonl 里的 8 段内容各存成一个 txt 文件上传（文件名用 policy_return_v3.txt 这种，与评测集的 doc_id 一致）。
  3. 开启引用：在应用编排里打开「引用和归属」。不开的话 retriever_resources 为空，检索指标直接记 0 分。
  4. 取 Key：应用「访问 API」页面创建密钥，形如 app-xxxxxxxx。写进环境变量 DIFY_API_KEY，不要提交到仓库。
  5. 跑自检：python demo.py doctor --suite configs/suites/dify_smoke.json，看 doc_id 覆盖率是否 100%。
  6. 跑评测：python demo.py run --suite configs/suites/dify_smoke.json，看报告第一屏的通过率。
# Windows PowerShell
$env:DIFY_API_KEY = "app-xxxxxxxx"

# macOS / Linux
export DIFY_API_KEY="app-xxxxxxxx"

# 自托管改 base_url，云端用 dify_cloud.json
python demo.py doctor --suite configs/suites/dify_smoke.json
python demo.py run    --suite configs/suites/dify_smoke.json
04

字段映射：Dify 响应 → 评测模型

映射全部写在配置里，代码里没有一个硬编码字段名。换厂商只改 JSON，这是"可替换"验收项的落地方式。

Dify 响应字段映射到用途配置键
answerAnswer.text生成指标、拒答判定answer_path
metadata.retriever_resourcesAnswer.contexts[]检索与忠实度contexts_path
document_namePassage.doc_id与评测集 golden 对齐doc_id_field
segment_idPassage.chunk_id精确到片段算 hit / MRRchunk_id_field
contentPassage.text忠实度判定依据text_field
scorePassage.score人工看召回质量score_field
最关键的取舍：用 document_name 而不是 document_id。
document_id 是 UUID，每次重建知识库都会变，评测集没法写死；document_name 是文件名，稳定且可读。配置里 doc_id_strip_suffix: true 会把 .txt 去掉，从而与 policy_return_v3 对上。
"mapping": {
  "answer_path": "answer",
  "contexts_path": "metadata.retriever_resources",
  "doc_id_field": "document_name",
  "chunk_id_field": "segment_id",
  "text_field": "content",
  "score_field": "score",
  "doc_id_strip_suffix": true
}
05

doctor 报出的三类典型故障

接真实系统时 80% 的时间耗在这三件事上。工具把它们变成三条可直接执行的提示，而不是让你盯着响应体找差异。

doctor 输出真实原因改哪里
鉴权失败（401）Key 不属于该应用 / 已失效 / 少了 Bearer 前缀重新创建应用密钥，确认 api_key_env 指向的变量有值
所有探测用例都没有返回引用片段应用没开「引用和归属」，或 contexts_path 写错编排页打开引用；确认路径是 metadata.retriever_resources
doc_id 覆盖率 0%，且列出两串 ID 对照用 UUID 去对文件名，或后缀没去掉doc_id_field 改 document_name，doc_id_strip_suffix 设 true
 
$ python demo.py doctor --suite configs/suites/dify_smoke.json --limit 3

06

六个常见坑

坑表现处理
多轮上下文污染同一 conversation 里，后一条问题带上前一条的答案，指标虚高适配器默认不传 conversation_id，且每条用例独立 user，已内置
流式响应response_mode=streaming 返回 SSE，解析不到 JSON评测用 blocking；流式留给"首 token 延迟"专项测试
限流并发 8 时大量 429，被算成采集失败concurrency 设 1-2，错误分类里 429 标为可重试
引用为空检索指标全 0，误判"检索差"先跑 doctor 确认是否开了引用
知识库重建segment_id 变了，历史基线不可比报告里记录 target 版本；重建后重跑基线，不做跨版本对比
答案改写模型润色导致 answer_match 偏低，但语义是对的v0 的 bigram 近似只作冒烟；语义判定交给 v1 的 judge

08

阶段一选靶子的三条标准

阶段一练的是工程能力，不是业务复杂度。所以靶子的标准很具体：

  1. 有公开且稳定的 API 文档，能直接用 curl 打通。否则你会把时间耗在猜接口上。
  2. 能造脏数据：允许你提交非法字段、超长字符串、重复数据，并能清理。只读接口练不出数据生命周期管理。
  3. 有真实的失败分支：401、404、422、429 至少覆盖三种。全 200 的靶子练不出错误断言。
不要选：需要企业认证的、接口随时变的、文档只有截图的、注册要手机验证码的。这些会把学习时间消耗在环境上。

10

真实开源仓库练手

公开靶场解决"能不能写"，真实仓库解决"别人认不认"。这类练手的产出是可验证的第三方证据，比自建 demo 有说服力得多。

仓库可贡献什么难度为什么适合
open-webui补 pytest 用例、修 e2e flaky、补 CI 步骤低测试目录结构清晰，维护者响应快
dify补 API 异常分支用例、补测试文档中与你的主靶子同源，理解成本低
ragflow补解析与检索的单测、复现文档中测试覆盖相对薄弱，机会多
langflow补后端组件单测、修 CI 配置中Python 技术栈一致
anythingllm补接口契约测试、文档示例可执行化低Node 栈，适合练跨栈阅读
判断一个仓库值不值得投入：近三个月有合并记录、CI 是绿的、有 CONTRIBUTING、维护者会回 PR 评论。四条缺两条就换一个，别在死仓库上耗时间。
11

第一个 PR 怎么提

不要一上来改核心逻辑。测试类 PR 的接受度远高于功能改动，因为风险低、收益明确。

路径具体做法接受概率
补覆盖缺口跑 pytest --cov，找 0 覆盖的关键函数，补 3-5 条用例高
修 flaky找 CI 里反复红又反复绿的用例，定位时序/共享状态问题高
为已修 bug 补回归测试翻最近修复的 issue，补一条能复现原问题的用例最高
文档示例可执行化把 README 里的 curl 变成可跑的测试脚本中
改核心逻辑除非你非常确定，否则第一阶段别碰低

PR 描述模板（直接套）

## 背景
该函数在 xxx 分支下没有测试覆盖，改动时容易回归。

## 改动
新增 4 条单元测试，覆盖：
- 空输入
- 超长输入（10000 字符）
- 数据库异常时的回滚
- 并发调用下的幂等性

## 验证
本地 `pytest tests/xxx -q` 全绿；覆盖率 42% -> 67%。

## 说明
只加测试，不改实现。若需要调整测试目录结构请告知。
三条纪律：一个 PR 只做一件事；改动控制在 200 行以内；先开 issue 问一句"要不要补这个测试"，再动手。后者能省掉一半白工。
